# AI 复核未匹配记录

本文件详细说明引擎 9 层匹配跑完后，AI 亲自阅读未匹配记录并用语义理解做最终判断的完整流程。SKILL.md 第六步概述了何时进入复核，这里提供完整的操作细节和 subagent 提示词。

---

## 核心思路

引擎 9 层匹配跑完后，AI 亲自阅读未匹配记录，用语义理解做最终判断，减少人工核查工作量。引擎已内置分层复核流程（`--ai-review`），AI 判断结果会写回核对底稿（匹配类型以 `AI:` 开头），无需手动拼接。

流程分两层：**按月分批 → 判断执行（小批直判 / 大批 subagent 并行）**。未匹配记录全量导出，不做任何规则预筛——AI 复核就是为了减少人工复核量，数据不全会导致组合判断（N:1 凑数）无法进行。

---

## 进入门槛

| 原始未匹配数量（任一侧） | 处理方式 |
|-------------------------|---------|
| ≤ `--ai-review-limit`（默认 500） | 引擎导出 → 用户确认后 → 分层 AI 复核 |
| > `--ai-review-limit` | 不做 AI 复核（引擎自动跳过并继续输出底稿）。未匹配过多说明范围没对齐，先回去解决范围问题（见SKILL.md"判断3B"），不要硬复核 |

未匹配过多时 AI 逐笔读是没有效率的——正确做法是修范围再重跑，而不是复核几百条本可以匹配上的记录。

---

## 复核前置确认（用户 gate）

引擎跑完（满足进入门槛、导出复核文件）后，AI 不能直接开始逐条审查。先向用户展示当前核对结果，把是否复核的选择权交给用户：

> **当前核对结果：**
> - 金额匹配率：99.2%　条数匹配率：98.4%
> - 未匹配：银行流水 112 条 / 序时账 42 条（按月分布：2025-01 6/1、2025-03 2/0、2025-04 2/0、2025-05 15/0、2025-06 87/41）
>
> 是否对剩余记录进行 AI 复核？
> - **[A] 进行 AI 复核**：AI 逐条审查全部未匹配记录，可匹配的自动写入底稿，剩余记录给出业务分类（预计 X 分钟）
> - **[B] 不复核**：直接生成核对底稿，剩余记录交人工核查
> - **[C] 先修范围/数据**：匹配率过低时建议先按"判断3B"修范围再重跑

- 匹配率、未匹配数来自阶段1 **普通核对**（不带 `--ai-review` 的首次运行）的引擎输出，按月分布来自 `ai_unmatched_*.json` 导出文件，AI 原样展示，不省略
- 用户选择 **[A]** 后才进入"逐条审查"流程；选 **[B]** 保持阶段1 普通核对底稿即可（不进入 AI 复核，已导出的复核文件保留备用）；选 **[C]** 回到判断3B
- 与客商 gate、多账户 gate 同理：用户明确选择后才能继续

---

## 第1层：按月分批（引擎导出时自动拆分）

未匹配记录按月份拆分为多个文件，每批包含该月全部未匹配记录（未做任何筛选）：

```
ai_review/ai_unmatched_2025-01.json   ← 每批一个文件
ai_review/ai_unmatched_2025-06.json
```

- 各批 idx 是全局行标识，跨批不重叠
- 引擎匹配逻辑本身是同月、AI 组合推理限定同月，按月分批天然合理且单批规模可控
- 金额唯一性/组合判断均基于批内全量数据（该月全部未匹配），不做抽样

---

## 第2层：判断执行（小批直判 / 大批 subagent 并行）

| 批内候选数 | 执行方式 |
|-----------|---------|
| < 50 条 | 主 AI 直接读该批判断（避免 subagent 启动开销） |
| ≥ 50 条 | 每批一个 subagent 并行判断（提示词模板见下） |

主 AI 汇总各批结果 → 检查 idx 无重复 → 统一写入 `ai_matches.json` → 重跑生成底稿。

---

## 操作方法

工作流分三阶段，匹配率必须先跑普通核对获得，避免在未展示结果前进入复核：

```bash
# 阶段1：普通核对（不带 --ai-review），生成底稿并打印各账户匹配率
python scripts/bankflow_reconcile.py config.json --output 核对底稿.xlsx
#   → AI 向用户展示匹配率/未匹配数，用户选择 [A] 后才进入 AI 复核

# 阶段2：加 --ai-review 重跑 → 引擎导出未匹配记录（不写核对底稿）
python scripts/bankflow_reconcile.py config.json --output 核对底稿.xlsx --ai-review ai_review/

# 阶段3：AI 判断后写 ai_matches.json，再次重跑同一命令 → 生成含 AI 复核的核对底稿
python scripts/bankflow_reconcile.py config.json --output 核对底稿.xlsx --ai-review ai_review/
```

### 阶段1 结束后的流程

1. **复核前置确认**：向用户展示匹配率、未匹配数（含按月分布），询问是否进行 AI 复核（见上文"复核前置确认"）。匹配率/未匹配数来自阶段1 普通核对的引擎输出（本命令因复核未完成不打印最终匹配率），AI 原样展示。用户选择 [A] 后才继续第 2-4 步；选 [B] 则保持阶段1 的普通核对底稿即可，不进入 AI 复核
2. AI 阅读总览 `<ai_review>/ai_unmatched.json`（全部未匹配记录，未做任何规则预筛）
3. 按月批次文件 `<ai_review>/ai_unmatched_YYYY-MM.json`（候选 ≥50 条的批交给 subagent 并行判断）
4. AI 逐条审查全部未匹配记录（银行 + 序时账每一条，不只是找几组匹配就收工），结果写入 `<ai_review>/ai_matches.json`

### 全量审查要求

AI 把每条未匹配记录都判断过——确认可匹配的写入 `matches`；无法匹配的写入 `unmatched` 并给出业务分类和理由。全部审查完才置 `"reviewed_all": true`。只匹配几组就重跑等于复核不完整，不应交付。

### ai_matches.json 格式

```json
{
  "matches": [
    {"bank_idx": 753, "gl_idx": 3418, "type": "AI:语义对手-高", "note": "判断依据"},
    {"bank_idx": [753, 1232], "gl_idx": [3418], "type": "AI:组合推理-高", "note": "两笔收款合计=GL一笔"}
  ],
  "unmatched": [
    {"idx": 667, "side": "bank", "分类": "个人卡代收货款-存疑", "note": "金额组合多解，无法唯一对应，建议人工核实"},
    {"idx": 4110, "side": "gl", "分类": "冲销红字-内部调账", "note": "冲5月558#凭证，净额0，无银行流水对应"}
  ],
  "reviewed_all": true
}
```

- `bank_idx` / `gl_idx` 为未匹配记录中的 idx，支持 N:1 组合（多笔银行 = 一笔 GL，用列表）
- `unmatched` 的 `side` 取值 `bank` / `gl`（两侧 idx 可能相同，用 side 区分）
- `分类` 参考枚举：个人卡代收货款-存疑 / 微小交易-手续费 / 冲销红字-内部调账 / 一收一支循环-净额0 / 无对应-跨科目跨期 / 待人工核实
- 引擎做金额硬校验：两侧金额合计必须相等（容差 1 元），不相等自动跳过并告警
- AI 判断无把握的匹配就不写，但该记录出现在 `unmatched` 中说明原因

5. 重新运行阶段1 的同一命令 → 生成核对底稿，AI 复核的匹配自动写入（匹配类型 `AI:` 开头）。`unmatched` 分类齐全且 `reviewed_all: true` 代表 AI 已全量审查完成。

## subagent 提示词模板

候选 ≥50 条的批，每批一个，并行执行：

> 你是银行流水核对 AI 复核员。请阅读未匹配记录文件 `<ai_review>/ai_unmatched_YYYY-MM.json`（bank_unmatched / gl_unmatched，字段：idx/日期/金额/方向/对手/凭证号/摘要）。该文件包含本批全部未匹配记录，未做任何筛选——组合推理和金额唯一性判断必须基于文件内全量数据。
>
> 按以下三个层次判断（只对同月记录做，跨月交给引擎 L9）：
> 1. **语义对手匹配**：同月 + 金额相同（±0.01）+ 双面有对手，名称语义是否同一对象（全称 vs 简称、括号别名、"供应商：/客户："前缀 vs 裸名）。真不同对象不匹配。
> 2. **组合推理**：金额有凑数关系时做子集和（如 3 笔银行合计 = 1 笔 GL）。用"唯一金额锚点"判断可信度：组合中存在全月只有一笔的金额 → 高可信；全是常见整数金额（100,000/500,000 等）→ 只标存疑，不断言。
> 3. **模式分类**：无法匹配的记录按业务原因分类（零金额/微额手续费、冲销红字、记录粒度差异、无对手信息、跨科目交易）。
>
> 输出（严格 JSON，必须覆盖本批全部记录——每条 idx 要么在 `matches`，要么在 `unmatched`）：
> ```json
> {"matches": [{"bank_idx": 753, "gl_idx": 3418, "type": "AI:语义对手-高", "note": "判断依据"}],
>  "unmatched": [{"idx": 667, "side": "bank", "分类": "个人卡代收货款-存疑", "note": "..."}],
>  "reviewed_all": true}
> ```
> 硬约束：两侧金额合计必须相等（容差 1 元）；idx 必须是文件中的值（支持列表组合）；无把握的匹配不写但必须在 `unmatched` 中分类说明；不要臆造对手关系；不得只输出几组 matches 就结束。

subagent 并行跑完后，主 AI 合并各批 `matches` + `unmatched` → 检查 idx 无重复 → 统一写入 `ai_matches.json` 并置 `reviewed_all: true`。

---

## AI 判断的三个层次（按顺序执行）

### 层次1：语义对手匹配（最高价值）

同月 + 金额相同（±0.01）+ 双面有对手，但引擎模糊匹配（rapidfuzz）没认出的组合。AI 判断名称语义是否同一对象：

- 全称 vs 简称："重庆金翘楚商贸有限公司" vs "金翘楚" ✅
- 括号别名："崇州市崇阳王氏新廉鑫食品经营部（王直刚）" vs "王氏新廉鑫" ✅
- 含"供应商：/客户："前缀 vs 裸名 ✅
- 真不同对象（金额巧合相同）→ 不匹配

### 层次2：少量组合推理

未匹配记录 ≤ 10 笔且金额有倍数/凑数关系时，AI 可心算子集和（如 3 笔银行转存合计 = 1 笔 GL 货款）。只对同月记录做，跨月交给引擎 L9。

**组合可信度判断——"唯一金额锚点"：**
- 组合中存在唯一金额（银行只有一笔该金额）→ 以它为锚点，组合可信度高
- 组合中全是常见金额（100,000/500,000/整数）→ 组合不唯一，只标存疑，不断言
- 示例：GL 借 977,400（宜宾静友货款），银行组合 500,000+477,400=977,400，其中 477,400 全月只有一笔 → 高可信匹配；而 GL 借 550,000（金翘楚），银行 50,000+500,000 / 70,000+480,000 多种组合 → 存疑，交人工确认

用 Python 快速验证组合（2 笔组合 O(N²) 秒级，3 笔以上用哈希/回溯，只对同月同向记录做）。

### 层次3：模式分类解释（兜底）

无法匹配的记录按业务原因分类，输出给用户：

| 模式 | 判断方法 |
|------|---------|
| 零金额/微额（手续费、利息） | 金额 < 1 元，GL 通常汇总入账 |
| 冲销红字（负数凭证） | GL 负金额，与正数配对净额为零 |
| 记录粒度差异 | 银行毛额 vs GL 净额（转取 vs 工资/材料款） |
| 无对手信息 | 单面无交易对手，无法语义判断 |
| 跨科目交易 | 理财/证券等记在其他科目 |

---

## 输出说明

- 核对底稿中的 AI 复核匹配：匹配编号正常编号，匹配类型以 `AI:` 开头，方便审计人员区分
- 引擎执行结束会提示"核对底稿已包含 N 笔 AI 复核匹配"
- 已匹配但需人工复核的差异（如交易对手名称不同），仍按核对明细的"交易对手核对"列展示

## 效率说明

- 引擎导出未匹配记录：< 1 秒（复用核对内存数据，不是重新读文件）
- AI 语义判断：小批直判 + 大批 subagent 并行，总耗时 ≈ 最慢一批
- 整体增量 < 2 分钟，远低于人工核对 100+ 笔的时间
